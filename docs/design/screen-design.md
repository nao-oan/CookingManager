## 2. デザイン方針

S-1 のデザイン探索（4コンセプト×3案＋b1系9案）から、**「冷蔵庫の食材を起点に、期限の近いものから献立を決めさせる」**案を採用した。

| # | 方針 | 根拠 |
|---|---|---|
| 1 | 期限の切迫度を色で段階表示する | 使い切りの判断を色だけで済ませる（F5-4, F5-5） |
| 2 | 食材を選ばせてからレシピを提示する | 「何があるか」から「何を作るか」へ思考を繋ぐ（F6-1） |
| 3 | 不足食材は点線枠で示し、在庫ありと並置する | 足りない1品が一目で分かる（F6-3） |
| 4 | 主要操作は画面下半分に置く | キッチンで片手・親指操作（NFR-8, NFR-9） |
| 5 | 削除は必ず確認を挟む | 誤操作の防止（NFR-10） |

## 5. 画面別定義

### L-1 ランディング `/`

| 項目 | 内容 |
|---|---|
| 目的 | 未ログインの訪問者に機能を説明し、登録へ導く |
| 機能要件 | F1-1 への導線 |
| 主要UI | キャッチコピー「冷蔵庫の残りから、今日の献立を。」／機能3点カード（レシピ登録・食事記録・在庫からレシピ提案）／かんたん3ステップ図／「はじめる」「ログイン」の2ボタン |
| 状態 | ログイン済みでアクセスした場合は S-1 へ自動遷移 |

| 備考 | 下部タブを表示しない |

### S-1 レシピ提案 `/suggestions`

**ログイン後の初期表示画面。** デザイン言語の基準となる画面。

| 項目 | 内容 |
|---|---|
| 目的 | 在庫から作れるレシピを不足の少ない順に見て、今日の献立を決める |
| 機能要件 | F6-1〜F6-7、F5-4、F5-5 |
| 主要UI | ①挨拶 ②「いま使いたい食材」= 期限バンド3件（色分け＋チェックボックスで選択）③「おすすめの組み合わせ」= レシピカード（料理名・`食材 4/4`・材料タグ）④「この組み合わせで作る」ボタン ⑤下部タブ（提案がアクティブ） |
| 並び順 | 不足食材の少ない順。不足0件のレシピを上に置く（F6-2） |
| 不足の表現 | 在庫ありの材料は色つきタグ、**不足している材料は点線枠のタグ**（`.tag--missing`）。充足数は `食材 3/4` の形式（F6-3） |
| 在庫の合計 | 同一食材の在庫が複数ある場合は合計数量で充足を判定する（F6-5） |
| 単位変換不可 | 数量比較できない組み合わせは `在庫あり（数量不明）` と明示（F6-6） |
| 常備食材 | 不足判定から除外し、タグにも出さない（F6-4） |
| 期限切れ | 在庫計算から除外する（F5-5） |
| 状態 | **空状態A**: レシピ0件 → レシピ登録への導線（F6-7）／**空状態B**: 在庫0件 → 在庫登録への導線（F6-7）／全レシピに不足がある場合は不足の少ない順に並べて表示 |
| 遷移 | レシピカード → R-2 ／ 設定アイコン → C-1 ／「冷蔵庫の食材を編集」→ P-1 |

## 7. 不採用とした要素

デザイン探索の過程で生成したモックアップには、要件定義書にない要素が含まれている。**下記7点は不採用**とし、HTML からは削除済み。PNG には写り込んでいるので読み替えること。

| # | 要素 | 判断 | 理由 |
|---|---|---|---|
| 1 | レシピ写真の添付 | **不採用（#34 で確定）** | Supabase Storage の設定、アップロードとリサイズ、RLS が必要で MVP の範囲を超える。`.thumb` は名前から選んだ絵文字で埋める（[8章](#8-未確定事項34-で解消済み)） |
| 2 | 在庫の保存場所（冷蔵／冷凍／常温） | 不採用 | F5-1 にない項目。入力が1つ増え、NFR-9 の3タップを圧迫する |
| 3 | レシピの分量切り替え（`2人分`） | 不採用 | F6-1 の不足算出と F6-5 の合計判定に倍率が絡み、提案アルゴリズムが複雑化する |
| 4 | レシピのカテゴリ（和食／洋食／時短） | 不採用 | F3-3 の料理名検索で足りる。個人用でレシピ件数が少ないうちは分類の価値が低い |
| 5 | レシピの所要時間（`約15分`） | 不採用 | F3-1 にない項目 |
| 6 | お気に入り（♡） | 不採用 | 自分が登録したレシピのみのため、絞り込みの必然性が薄い |
| 7 | 通知ベル／「このアプリについて」／「利用規約・プライバシー」 | 不採用 | 通知基盤は MVP に重い。個人用のため規約も不要 |

**1について。** `.thumb` は現状 `🍗` `🥬` のような絵文字のプレースホルダで、フェーズ7で実画像に差し替える。差し替えが `.thumb` の中身だけで完結するよう、寸法と角丸はクラス側に持たせてある。

この7点はいずれも要件定義書への追記を伴わない。`docs/spec/cooking-manager-requirements.md` は変更しない。

## 8. 未確定事項（#34 で解消済み）

設計を進める中で判断が必要になった項目と、その結論。

| # | 項目 | 影響する画面 | 結論 |
|---|---|---|---|
| 1 | 在庫やレシピから参照されている食材を削除しようとしたときの挙動 | C-3 | **禁止する。** `ON DELETE RESTRICT` とし、C-3 で参照件数を示して止める（[DB設計 4章](database.md)） |
| 2 | 単位の選択肢と変換ルールの定義場所 | R-3、R-4、P-2、P-3、C-3 | **12種の列挙型。** 換算は質量・容量のみで、アプリ層（`src/domain/unit/`）に置く（[DB設計 3章](database.md)） |
| 3 | パスワード再設定の画面 | A-1 | **実装する。** A-3（依頼）と A-4（設定）を追加した。メールのリンクは `/auth/callback` で受ける |
| 4 | S-1 で提案するレシピの表示件数と、それ以上を見る導線 | S-1 | **既定10件＋「もっと見る」。** 算出は全件行い、表示だけを絞る。「もっと見る」で残りを開く |
| 5 | `.thumb` のプレースホルダを何で埋めるか | 全画面 | **名前から絵文字を選ぶ。** `src/domain/thumbnail/` の純関数で、食材名・料理名のキーワードから決定的に選ぶ |

### 4について

件数を絞るのは表示だけで、並べ替えと不足判定は全件に対して行う。上位10件に入らなかった案も「もっと見る」で同じ並び順のまま続きを見られる。ページングにしないのは、個人用でレシピ件数が数十のうちは1回の取得で足り、状態管理が増えるだけのため。

### 5について

固定の絵文字を直書きすると、どのカードも同じ見た目になり一覧で見分けがつかない。名前から選べば、登録した食材・レシピの種類が一目で分かる。実画像に差し替える場合も、関数の戻り値を画像URLに変えるだけで済む。

### レシピ写真の添付（7章1）について

**見送る。** 要件定義書に項目がなく、Supabase Storage の設定・アップロード・リサイズ・RLS が必要で MVP の範囲を超える。`.thumb` を上記5の方式で埋めたため、写真がなくても一覧の見分けはつく。必要になった時点で、`ingredientThumbnail` / `recipeThumbnail` の戻り値を画像URLに差し替える形で入れられる。

## 9. Figma への取り込み

`html.to.design` プラグインでレイヤー化して取り込める。手順は次のとおり。

1. Figma で `html.to.design` をインストールする
2. **Import from code** タブを開く
3. `mockups/html/dist/<画面ID>.html` の中身を全文コピーして貼り付ける
4. Import を実行すると、テキスト・矩形・オートレイアウトを持つレイヤーとして展開される

CSS を変更したときは `node docs/design/mockups/html/build-standalone.mjs` を再実行して `dist/` を更新する。Google Fonts（Noto Sans JP / Zen Maru Gothic）は Figma 側で利用可能にしておく。
