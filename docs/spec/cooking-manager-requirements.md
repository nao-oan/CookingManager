# CookingManager 要件定義書

## 1. 概要

日々の料理を管理するクラウドWebアプリケーション。レシピを登録し、食べたものを記録し、冷蔵庫の在庫から「いま作れる料理」を買い足しの少ない順に提案する。

スマートフォンのブラウザからキッチンで使うことを主用途とする。個人利用（1アカウント＝1人分のデータ）。

### スコープ

| 区分 | 内容 |
|---|---|
| MVPに含む | 認証、レシピ登録、食事記録、在庫管理、在庫マッチングによるレシピ提案 |
| 含まない | AIレシピ生成、外部サイト取り込み、栄養計算、世帯共有、買い物リスト、写真、通知、献立プラン |

### 用語

| 用語 | 定義 |
|---|---|
| 食材 | レシピの材料および在庫の対象となるもの |
| 常備食材 | 塩・醤油・油など、在庫管理せず「常にある」とみなす食材。提案の不足判定から除外する |
| 在庫 | 現在保有している食材。数量・単位・賞味期限を持つ |
| 不足食材 | レシピに必要だが在庫で賄えない食材 |

## 2. 機能要件

### F1. アカウント

- F1-1: メールアドレスとパスワードでユーザー登録・ログインできる
- F1-2: ログイン中のユーザーは自分のデータのみ参照・操作できる
- F1-3: ログアウトできる

### F2. 食材

- F2-1: 食材（名称、標準単位、常備食材フラグ）を登録・編集・削除できる
- F2-2: レシピ・在庫の入力時に、既存の食材を名称の部分一致で検索して選択できる
- F2-3: 同名の食材が既にある場合、候補として提示し重複作成を防ぐ

### F3. レシピ登録

- F3-1: レシピ（料理名、材料リスト、手順、メモ）を登録・編集・削除できる
- F3-2: 材料は「食材・数量・単位」の組で保持する。材料は最低1件必須
- F3-3: レシピを一覧表示し、料理名で検索できる
- F3-4: レシピ詳細で、各材料が現在の在庫で賄えるかを材料ごとに表示する

### F4. 食事記録

- F4-1: 日付と食事区分（朝食／昼食／夕食／間食）を指定して食事を記録・編集・削除できる
- F4-2: 記録の内容は「登録済みレシピの選択」または「自由入力テキスト」のいずれでもよい
- F4-3: 1回の食事に複数の品目を登録できる
- F4-4: 記録を日単位およびカレンダー（月）単位で閲覧できる

### F5. 在庫管理

- F5-1: 在庫（食材、数量、単位、賞味期限）を登録・編集・削除できる。賞味期限は任意
- F5-2: 在庫一覧を賞味期限の近い順に表示できる
- F5-3: 一覧から数量を直接増減でき、0になった在庫は既定表示から外れる
- F5-4: 賞味期限が3日以内の在庫を警告表示する
- F5-5: 賞味期限切れの在庫は区別表示し、提案の在庫計算から除外する

### F6. レシピ提案

- F6-1: 在庫と各レシピの材料を突き合わせ、レシピごとの不足食材を算出する
- F6-2: レシピを不足食材の少ない順に並べて提案する
- F6-3: 各レシピについて、不足食材の名称と不足数量を表示する
- F6-4: 常備食材は不足判定の対象から除外する
- F6-5: 同一食材の在庫が複数ある場合、合計数量で充足を判定する
- F6-6: 単位が異なる場合、変換ルールがあれば換算して判定する（g⇔kg、ml⇔L）。変換できない組み合わせ（例:「個」⇔「g」）は数量比較を行わず「在庫あり（数量不明）」として明示する
- F6-7: レシピまたは在庫が0件の場合、登録への導線を含む案内を表示する

## 3. 非機能要件

### パフォーマンス

- NFR-1: 主要画面（レシピ一覧、在庫一覧、提案）の初期表示が3秒以内
- NFR-2: 提案の算出が、レシピ200件・在庫100件の規模で1秒以内
- NFR-3: 提案の算出はサーバー側で行い、クライアントへ全レシピを転送しない

### セキュリティ

- NFR-4: 他ユーザーのデータへのアクセスを、アプリケーション層とDB層の双方で遮断する
- NFR-5: パスワードはハッシュ化して保存する
- NFR-6: 全通信をHTTPSで行う
- NFR-7: 認証情報・APIキーをリポジトリにコミットしない

### ユーザビリティ

- NFR-8: スマートフォン（375px幅）で横スクロールが発生しない
- NFR-9: 在庫の追加、食事の記録がいずれも3タップ以内で完了する
- NFR-10: 削除操作は実行前に確認を求める
- NFR-11: UIは日本語。日時はAsia/Tokyoで表示し、保存はUTCで行う

### 保守性

- NFR-12: データモデルはマイグレーションでバージョン管理する
- NFR-13: 提案アルゴリズム（充足判定・不足算出・単位変換）は独立モジュールとし、単体テストを用意する
- NFR-14: 将来の世帯共有に備え、データの所有者を単一のオーナーIDで表現する

### 運用

- NFR-15: 無料枠または低コストで運用できるホスティング・DB構成とする
- NFR-16: モダンブラウザ（Chrome / Safari / Edge の最新2バージョン）で動作する

## 4. 技術要件

### 構成

| 項目 | 選定 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型でドメインの誤りを早期に検出する。フロント・サーバー間で型を共有する |
| フレームワーク | Next.js（App Router） | Server Components / Server Actions により、提案の算出をサーバー側で完結できる（NFR-3） |
| UI | Tailwind CSS + shadcn/ui | スマホ幅（375px）のレイアウト調整が書きながら詰められる（NFR-8）。shadcn はコードを自リポジトリに取り込む方式で依存を増やさない |
| バックエンド | Next.js Server Actions / Route Handlers | 別サービスを立てず、単一デプロイで完結させる |
| データベース | Supabase（PostgreSQL） | 提案アルゴリズムが在庫 × レシピ材料 × 食材の結合であり、リレーショナルDBが適する（NFR-2） |
| データアクセス | Drizzle ORM | 型安全なクエリと、マイグレーションのバージョン管理（NFR-12）。RLS と併用できる |
| 認証 | Supabase Auth | メール＋パスワード認証（F1-1）を自前実装せずに済む。パスワードのハッシュ化も担保される（NFR-5） |
| アクセス制御 | PostgreSQL RLS（行レベルセキュリティ） | DB層で他ユーザーの行を遮断する。アプリ側の実装漏れが情報漏洩に直結しない（NFR-4） |
| ホスティング | Vercel | Next.js の標準的な実行環境。GitHub 連携により main への push で自動デプロイ（1-6） |
| CI | GitHub Actions | Lint・型チェック・単体テスト・ビルドを PR ごとに実行（1-5） |
| 単体テスト | Vitest | 提案アルゴリズムを独立モジュールとして高速に検証する（NFR-13） |
| E2Eテスト | Playwright | 主要導線の回帰確認。フェーズ7で導入する |
| Lint / Format | ESLint + Prettier | — |

### 提案アルゴリズムの実行場所

**アプリケーション層（TypeScript）で実装する。** DB関数（SQL）としては実装しない。

- レシピ200件・在庫100件の規模（NFR-2）であれば、TypeScript による突き合わせで十分に1秒以内に収まる
- 純粋関数として切り出すことで単体テストが容易になる（NFR-13）
- 単位変換・常備食材の除外・並び順といったロジックが SQL より読みやすく、変更に強い

データ取得はサーバー側で行い、クライアントへ全レシピを転送しない（NFR-3）。将来的に性能が問題となった場合は、事前計算またはDB側への移設を検討する。

### 却下した構成

| 案 | 却下理由 |
|---|---|
| Cloudflare Workers + D1 | D1 は SQLite ベースで RLS 非対応のため、NFR-4 のDB層での遮断を満たせない |
| Cloudflare Workers + 外部Postgres | RLS は維持できるが、Hyperdrive の構成が加わり手数が増える。単一ベンダーの利点も失われる |
| Firebase / Firestore | 提案アルゴリズムが複数テーブルの結合であり、NoSQL では全件突き合わせとなって NFR-2 を満たしにくい |
| Prisma | 型安全だが RLS との相性に難があり、NFR-4 の担保をアプリ層に頼ることになる |

### 既知の制約

- Supabase の無料プランは、7日間アクセスがないとプロジェクトが一時停止する。日常的に利用する前提のため運用上の支障はないが、長期間放置する場合は再開操作が必要となる
- Vercel・Supabase の2サービスに依存する。いずれも無料枠で開始し、必要に応じて有料プランへ移行する（NFR-15）

## 5. プロジェクト計画

### フェーズ一覧

| # | フェーズ | 内容 | 完了条件 |

| 0 | 要件定義・設計 | 要件定義、技術選定、サイトマップ、システム設計、画面設計、DB設計、ファイル設計 | 設計書一式が揃い、実装に着手できる |

| 4 | 在庫管理 | F5 | 在庫を登録し、期限順に確認できる |

成果物はすべて `docs/` 配下に置く。

### 方針

- フェーズ1で本番環境まで通す。クラウド前提のため、デプロイを最後に回さない
- 各フェーズは動く状態で区切り、実際に自分で使いながら次を決める
- フェーズ5までが本アプリの中核。ここまでを最優先とする
